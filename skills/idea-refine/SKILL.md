# Refine the Problem Before Committing the Solution

## Overview

Expand credible options, test hidden assumptions and converge on a useful bounded proposal. The output explains what will not be built and why.

## When to Use

Use for ideation, sharpening an early concept or stress-testing a plan before specification. Respect implementation requests once the idea is already settled.

## Process

### Frame the problem

Identify audience, current workaround, important pain and intended outcome. Ask a sharpening question before converging when these are missing. Distinguish evidence from optimism and avoid treating enthusiasm as validation.

### Surface assumptions that can fail

List adoption, operating, technical and scope assumptions that materially affect the concept. Choose a small observation or experiment for the weakest important assumption. Label untested market/user claims instead of inventing research.

### Expand relevant options

Consider a few meaningfully different approaches, including a simpler workflow or reuse of existing capabilities when credible. Compare them against the actual constraints. Do not generate a long novelty list disconnected from the user's need.

### Converge with reasons

Recommend a direction, its first useful outcome and the evidence needed before investing further. Push back on unsupported complexity or a mismatch between the proposed solution and user pain. Preserve explicit user choices unless a real tradeoff needs discussion.

### Define the boundary

Write an explicit **Not Doing** list: each exclusion has a reason tied to the first outcome. Record open questions, testable assumptions and the next decision. If producing an idea artifact, follow existing project conventions; optional helper scripts are not required.

Use `spec-driven-development` only once the selected direction is concrete enough to define behavior. A refined idea is not implemented, validated or guaranteed unique simply because the proposal reads well.

## Common Rationalizations

| Shortcut | Correction |
|---|---|
| Refinement means agreeing more clearly | Challenge weak assumptions with concrete reasons. |
| The MVP should cover every audience | Bound the first useful outcome and exclusions. |

## Red Flags

- Recommendations precede understanding the need.
- A proposal claims validation without evidence.
- Scope has no explicit exclusions.

## Verification

- [ ] Sharpening questions precede convergence where needed.
- [ ] Hidden assumptions and their checks are explicit.
- [ ] The recommendation has reasons and an explicit Not Doing list.
- [ ] The next decision is actionable and validation limits are honest.
