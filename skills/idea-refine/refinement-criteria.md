# Evaluate the Concept by Its Weakest Important Assumption

Use applicable questions rather than assigning invented scores.

| Criterion | Evidence to seek | Decision it changes |
|---|---|---|
| User outcome | Present task, pain and workaround | Whether the proposed feature solves the right problem |
| Adoption | Inputs/actions the user must supply | Whether the path is usable without ideal behavior |
| Scope | One independently useful first result | What belongs in the first release |
| Feasibility | Required contracts and available capabilities | Which option is implementable in this project |
| Operations | Maintenance owner and expected failure handling | Whether the team can sustain the result |
| Reversibility | Data, consumer and external-effect transitions | How to validate before costly commitment |

Choose the assumption whose failure would invalidate the proposal, then define a
small check that yields actionable evidence. A technical prototype cannot prove
users want the feature; positive interview feedback cannot prove provider reliability.

Record explicit Not Doing items and their reasons. Keep unknowns visible and avoid
presenting unverified market estimates, benchmarks or originality as facts.
