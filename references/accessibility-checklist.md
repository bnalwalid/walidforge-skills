# Verify the Interaction Is Available to the User

Use the product's chosen accessibility requirements and target platforms. This
checklist organizes evidence; it does not certify compliance by itself.

## Navigation and semantics

- [ ] Interactive controls have meaningful names, roles and states.
- [ ] Native platform/HTML controls are used where they express the interaction.
- [ ] Keyboard or platform navigation reaches actions in a coherent order.
- [ ] Focus is visible and remains meaningful after navigation or content changes.
- [ ] Modal opening, containment and return focus are verified in runtime.

## Understanding and recovery

- [ ] Labels, instructions and error messages are associated with their inputs.
- [ ] Status changes are conveyed without relying only on color or animation.
- [ ] Loading, empty and failure states offer an understandable next action.
- [ ] Destructive operations and validation preserve the user's context.

## Presentation and platform behavior

- [ ] Layout remains usable under text enlargement and relevant viewport/device sizes.
- [ ] Contrast and target sizes satisfy the project's selected requirements.
- [ ] Reduced motion and relevant platform accessibility settings are respected.
- [ ] Content structure and alternatives convey the information meaningfully.

## Evidence

- [ ] Automated checking uses an available running target and stated policy.
- [ ] Manual keyboard and relevant assistive-technology journeys complement scans.
- [ ] The account, route, runtime and checked states are recorded.
- [ ] Native evidence is distinguished from web prototypes and static inspection.
- [ ] Unchecked experiences and residual issues are explicit.
